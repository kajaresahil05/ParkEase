5. ENTRY FLOW
1. User logs in.
2. Views available slots.
3. Books a slot.
4. Backend reserves it.
5. Vehicle reaches entrance.
6. Entry IR detects waiting vehicle.
7. User presses ENTER PARKING.
8. Backend verifies authenticated user, active booking, correct vehicle, reserved slot, and unused entry
authorization.
9. Backend authorizes entry.
10. ESP32 receives authorization.
11. Servo opens.
12. Vehicle crosses gate.
13. Exit IR detects vehicle.
14. ESP32 reports entry-crossed.
15. Backend changes ENTERING → IDLE.
16. Gate closes.
17. Slot sensor detects vehicle.
18. Reserved slot becomes OCCUPIED.
Handle timing correctly so a slot report arriving after ENTERING → IDLE still changes the correct RESERVED slot to
OCCUPIED.
6. EXIT FLOW
1. Vehicle approaches exit.
2. Exit IR detects it.
3. ESP32 requests exit.
4. Backend identifies an OCCUPIED slot that becomes empty.
5. Slot becomes EXITING.
6. It must not immediately become AVAILABLE.
7. Gate opens.
8. Vehicle passes.
9. Entry IR confirms vehicle fully exited.
10. ESP32 reports completion.
11. EXITING → AVAILABLE.
12. Gate closes.
With only three slot sensors, exact vehicle-to-slot mapping cannot always be known. For the prototype, use the
occupied slot whose sensor changes OCCUPIED → EMPTY during active exit.
